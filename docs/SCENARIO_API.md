# Scenario API implementation contract

This additive contract is defined before implementation. Existing simulation envelope and three families from API_CONTRACTS are retained. The financial model below is an explicitly supplied, bounded aggregate model; it does not invent calendars, task allocations, approved rates, or observed business facts.

POST /api/simulations requires a session and Idempotency-Key (16–128 characters). Input: promise_id, base_graph_revision, question, scenario_types (unique, 1–3), assumptions (max 100), optional parent_scenario_id, optional financials, overlays (max 3). Every caller assumption must have kind USER_ASSUMPTION; OBSERVED claims must originate from authorized graph evidence, not clients. Assumptions carry id, description, optional value/unit, evidence_ref_ids. Evidence IDs must resolve in the caller tenant's PUBLIC_DEMO evidence.

financials: currency (three uppercase letters), scope_id, optional revenue, baseline_cost, required_hours, available_hours, hourly_cost. Numeric values are normalized nonnegative decimal strings, maximum 24 characters. All inputs are estimates. Null is unknown, never zero. overlays each contain type and optional required_hours, available_hours, hourly_cost, revenue, other_cost, delay_days, daily_delay_cost. Overlays are absolute alternatives, not increments. AS_REQUESTED cannot have an overlay; its scope is financials.scope_id. Unknown overlay fields inherit the baseline except delay and overhead, which require explicit values to calculate adjusted cost. No FX conversions or cross-scope cost summation.

201 returns {request_id,scenario_ids,results}. GET /api/simulations/{scenario_id} returns {request_id,scenario}. Reads require same tenant, original actor, accessible PUBLIC_DEMO promise and all retained source references. Results persist immutable captured receipt, inputs, overlays, estimates/explanations, version, digest and signed audit reference. New assumptions create new IDs; parent links preserve history. Idempotent replay is bound to tenant, actor and request digest. Revision/head checks atomically publish all results, replay ledger and signed audit event. Changed base revision returns 409; inaccessible inputs 404; invalid input 422; missing signing/graph configuration 503. Replay changes only request_id. GET marks status STALE when graph revision differs from the revision immediately after publication; this is deliberately conservative.

Each ScenarioResult retains the contract fields, with empty schedule, graph_paths, candidate_actions, policy_checks and null auditor where those capabilities have not been established. Inputs include the exact authorized receipt snapshot. affected_entity_ids includes promise and receipt. Missing calendar/dependency mapping always appears in missing_inputs. Aggregate positive capacity gap establishes INFEASIBLE within supplied assumptions; zero gap yields UNKNOWN, never a fabricated schedule or FEASIBLE claim. conditional is true because financials/overlays are caller assumptions. Formula outputs expose id, value/null, currency/unit, status ESTIMATE/UNKNOWN, explanation, input values, missing_inputs. Values are unrounded exact decimal strings. UI rounding is presentation only.

Implemented formulas: F01 estimated required_hours × hourly_cost; F04 max(0,required_hours−available_hours); aggregate cost SCENARIO_AGGREGATE_COST = required_hours × hourly_cost + other_cost + delay_days × daily_delay_cost (baseline uses zero adjustment, alternatives must supply adjustments explicitly); F06 cost−comparable baseline_cost; MARGIN_AMOUNT revenue−cost; MARGIN_PERCENT 100×margin/revenue (zero revenue unknown). F01 is not added to scenario cost; it describes overlapping scope. F02/F03/F05/F07 require milestone/allocation/approval evidence and remain outstanding rather than returning misleading successful outputs. Delivery delays are user-supplied cost assumptions, not predicted finish dates.

Remaining full product work: dependency/calendar scheduler, observed financial graph mappings, resource rates/allocations, milestone exposure/readiness, generated action candidates and policy/auditor. These are not fulfilled by aggregate calculations.

Validation observed 2026-10-14: 13 unit and 4 real FalkorDB integration tests passed via `PYTHONDONTWRITEBYTECODE=1 RUN_FALKORDB_INTEGRATION=1 .venv/bin/pytest tests/integration/test_scenario_publication.py tests/unit/test_scenarios.py -q -p no:cacheprovider` from backend/. Scenario-owned files pass Ruff. Graph tests include concurrent identical requests publishing once, retained source access change denying replay, parent history and full local signed audit verification. Tests use disposable graphs and generated signing keys. Existing Starlette TestClient deprecation warning remains.

Precision: products/sums use 100-digit Decimal context (input lengths bounded to 24); repeating percentage divisions round to that context and are not asserted as exact rational values. No currency presentation rounding is applied by the backend.
