# Teams and Jira connector contract and deployment

Connector clients perform real HTTPS requests; no configured connection is reported as a mock success. Live vendor validation requires separately supplied credentials and authorized test resources. Client HTTP errors are redacted and writes are never automatically retried.

Planned route contract (router factory must be registered by application): administrator session required; connections are selected from a server-owned tenant registry, never client URLs or credentials. `GET /api/connectors` reports configured types only. `GET /api/connectors/{connector_id}/health` performs a vendor read. `POST /api/connectors/{connector_id}/import` imports an identified Teams transcript or bounded Jira JQL result as a retained source via existing signed ingestion. JSON fields: Teams `organizer_id, meeting_id, transcript_id, access_label`; Jira `jql, access_label`. Requires `Idempotency-Key` 16–128 characters. Success is existing upload result; no inferred background sync or full historical synchronization. A source uses stable vendor identity, so subsequent import versions changed content. Source authorization labels are chosen by admin; vendor ACLs are not automatically mapped to application users. Returned connector failures use 502 without vendor response content. Missing tenant connection is 404.

Teams setup: register an application in Microsoft Entra ID; configure directory tenant ID, client ID and client secret through a secret manager. Application permission `OnlineMeetingTranscript.Read.All` requires admin consent and an application access policy assigned to the organizer. Supply a known authorized organizer and meeting ID; discovery enumerates transcripts within that meeting, not all tenant meetings. Client credentials request `https://graph.microsoft.com/.default` at the tenant v2 OAuth token endpoint. Access policy / licensing / recording retention may still restrict availability. VTT is retained verbatim as UTF-8 text with vendor identifiers; speaker/timestamp lines remain evidence, not inferred identities. No calendar discovery permission is assumed.

Jira setup: configure a tenant-specific HTTPS Cloud site, dedicated account email and API token, or OAuth bearer token with configured Cloud gateway base URL. Account must have Browse Projects and issue security access for reads, Edit Issues for updates. OAuth apps need vendor-approved scopes for their operations (classic read:jira-work and write:jira-work; user identity probe may additionally require read:jira-user). Tokens are server configuration only. Client accepts only a small field-update allowlist; transitions use their own API and are not implemented by field update. Jira issue count is not capacity: missing workload/capacity remains unknown. Client update/read-back is an adapter primitive; expose it only through durable, approved action execution with permission checks and reconciliation. Do not wire a direct unaudited public update endpoint.

Read retries: bounded retries for rate limits/transient HTTP failures and transport failures, capped Retry-After/backoff. Writes: one attempt; timeout/result ambiguity must be reconciled by read-back before another attempt. Pagination has a fixed bound and fails rather than silently truncating. Microsoft continuation URLs must stay under Graph HTTPS v1.0; credentials never follow arbitrary URLs or redirects.
